# Courier

Courier connects people who need an item with travelers already going that way. The app uses Next.js App Router, TypeScript, Tailwind CSS 4, PostgreSQL, and Prisma ORM 7.

## Local setup

1. Copy `.env.example` to `.env`, set `DATABASE_URL`, a private `AUTH_SECRET`, the public app URL, and working SMTP sender credentials.
2. Install dependencies with `npm install`. Prisma Client is generated by the npm `postinstall` hook.
3. Start the app with `npm run dev`.
4. Apply schema changes with `npx prisma migrate dev --name <migration-name>`.

Deployments should apply committed migrations with `npx prisma migrate deploy` as a release step. The app build generates Prisma Client but does not apply migrations. The project stays on Prisma 7.

## Authentication

Authentication uses Auth.js Credentials with Courier-managed email/password accounts. Registration is `POST /api/v1/auth/register`; sign-in is available only after email verification. Verification and recovery links are sent through SMTP configured with `SMTP_HOST`, `SMTP_PORT`, optional paired `SMTP_USER`/`SMTP_PASSWORD`, `SMTP_SECURE`, and `EMAIL_FROM`. Link tokens are random, stored only as SHA-256 hashes, expire, and can be used once. Password reset increments a session version so existing JWT sessions stop authorizing protected pages and APIs. Set `AUTH_SECRET` to a long random value before running the app.

New email lifecycle schema changes require a migration. In development, after configuring PostgreSQL, run `npx prisma migrate dev --name email_verification_and_password_recovery`; deployments should apply the committed migration with `npx prisma migrate deploy`.

Auth.js Credentials does not create or persist users by itself, so Courier stores users and password hashes in the existing `User` table. Recovery request responses do not reveal whether an account exists, and token requests have a per-account cooldown. Configure network-level throttling at the deployment edge before opening registration publicly.

## REST API

All browser and server-to-server operations use HTTP route handlers under `/api/v1`; the app does not use Server Actions for API requests. Request, itinerary, matching, agreement, and registration endpoints are documented in [openapi.yaml](./openapi.yaml). Protected endpoints scope data to the authenticated owner.

Matching checks whether the request origin and destination appear in order along a future itinerary, including declared intermediate stops. Travelers can add these stops in the journey form as city and country pairs. If both locations have coordinates, a waypoint within 30 km qualifies; otherwise normalized city and country names must match. A request's `neededBy` date is the latest acceptable itinerary arrival date. Matches remain suggestions until the traveler expresses interest.

Agreement endpoints start an agreement from an interested match, record versioned item-cost-plus-fee terms, require requester acceptance of the current revision, and prevent ordinary cancellation after funding. The traveler can start handoff only after a funded payment exists. The requester can record delivery only during handoff; the payment is then marked `RELEASE_PENDING`. Participants can report a handoff issue, which blocks release. Support operators listed in `COURIER_SUPPORT_USER_IDS` can inspect cases and move them into review through `/support/disputes`. Dispute adjudication and provider payout are not wired yet.

Payment code currently defines a provider-neutral server adapter contract only. No provider is selected, no payment initiation/webhook/payout API exists, and no code moves funds. `checkReleaseEligibility` is a read-only gate requiring a locked funded terms snapshot, matching pending payment amount/currency, requester delivery confirmation, and no dispute.

The liveness endpoint is available at `http://localhost:3000/api/v1/health`. The readiness endpoint at `/api/v1/ready` verifies database connectivity. The responsive `/dashboard` supports request, route, match, agreement, handoff, receipt-confirmation, and issue-reporting flows. Payment initiation and payout remain gated on provider integration.

## UI conventions

- Use Tailwind utilities for page and component layout, spacing, color, typography, and interaction states.
- Keep global CSS limited to theme tokens, base browser settings, and shared keyframes.
- Keep the application canvas white. Use Courier green for primary actions and quiet gold accents for route and status details.
- Use borders, spacing, color, and subtle motion for depth; do not use drop shadows or box shadows.
- Respect reduced-motion preferences for all nonessential animation.

## Project structure

- `src/app` - pages and REST route handlers.
- `src/auth.ts` and `src/app/api/auth/[...nextauth]` - Auth.js configuration and route handler.
- `src/lib/http` - response envelopes, request IDs, validation, and route error conversion.
- `src/lib/domain` - request, itinerary, matching, agreement, delivery, dispute, and release-eligibility services.
- `src/lib/payments` - provider-neutral payment adapter contract and normalized types; provider implementation is pending selection.
- `src/lib/auth` - password hashing, login throttling, auth boundary, and session helpers.
- `src/lib/db` - Prisma client boundary.
- `src/lib/logging` - structured server log helper.
- `docs/operations.md` - environment, readiness, support, and release notes.
- `prisma/schema.prisma` - marketplace and local authentication models.
- `prisma.config.ts` - Prisma 7 schema, migration, and generation config.
- `openapi.yaml` - current REST endpoint contract.
- `plan.md` - staged implementation roadmap.
